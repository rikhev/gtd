# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

Delegated: a TypeScript web app served locally. React + Vite on the front end, a small Node server (Hono) holding the Anthropic API key and file parsing, and SQLite for storage. Chosen because it keeps everything on one machine, keeps the API key off the client, and makes dense editable lists straightforward. It runs in the browser at localhost; a desktop wrapper can come later without a rewrite.

## Users

One person: the owner, on their own Mac. They practice (or want to practice) David Allen's Getting Things Done and want the capture → clarify → organize loop to take less effort. The expected power use is keyboard-heavy and list-centric, in the spirit of the classic Outlook Tasks view.

## Product Purpose

A personal GTD system where capture has no friction and clarification is assisted. The owner dumps "stuff" into an inbox by typing or uploading documents. On request, Claude processes the inbox and proposes outcomes for each item: projects, next actions, waiting-for, someday/maybe, reference, or trash. The owner accepts, edits, or rejects the proposals. The result lives in compact, directly editable lists.

Success means the inbox reaches zero regularly and every active project has a next action. The owner trusts the lists enough to work from them.

## Positioning

Clarifying is the GTD step people skip because it takes thought. This product hands that thinking to Claude as a proposal and keeps the human as the decision-maker. Nothing moves out of the inbox without the owner's say-so.

## Operating Context

- Runs locally in a browser tab (no login on localhost), or self-hosted on the owner's VPS at gtd.rikard.me behind HTTPS with a single-owner login: password + TOTP authenticator code, one-time recovery codes, 30-day HttpOnly sessions, and login rate limiting. There is one user and no sync between instances. Deployment is documented in DEPLOY.md.
- Capture comes from free typing (quick-add) and from uploaded documents. The accepted document types are still undecided.
- Clarification is triggered by an in-app action that calls the Claude API with the owner's own key.
- Includes a recurring Weekly Review ritual, which Claude may assist.

## Capabilities and Constraints

- GTD lists at launch: Inbox, Projects, Next Actions, Contexts (tags on next actions, e.g. @computer, @phone), Waiting For, Someday/Maybe, Reference, Weekly Review.
- The clarify step is proposal-based. Claude suggests and the owner decides.
- Project and next-action lists are compact, inline-editable tables/lists (the Outlook Tasks model).
- Next Actions are grouped by context by default (where the owner is and what tools are at hand); grouping by project is also offered (owner's request).
- Waiting For is grouped by who or what it waits on (Group by waiting on), never by project; the Waiting on column is hidden while grouped by it. A new item added inside a group offers that name first. The names offered when asking "waiting on" are the ones on items in Waiting For right now; an item moved back to Next or Someday drops its waiting on, since and follow-up (⌘Z brings them back).
- Next Actions and Waiting For can also be grouped by "flagged for today": a Today group first (dated on the right), then Everything else. A new action added inside the Today group is flagged for today.
- **Keyboard-only is a hard requirement.** The whole interface must work without a mouse. Every view, list, row, field, action, dialog, and Clarify decision needs a keyboard shortcut or a keyboard path. The mouse is optional and never required.
- Shortcuts follow **Outlook on the web** conventions, not classic desktop Outlook. On the Mac, Ctrl becomes ⌘ everywhere (owner's rule). The one exception is the go-to keys: Control+1–7 on every system, ⌃1–7 on the Mac too (owner's decision), because the browser owns ⌘1–8 (tabs), macOS owns ⌘⇧3–5 (screenshots) and ⌘⌥ is too awkward to hold. On Windows and Linux the page takes Ctrl+1–7 over the browser's tab switching. Mac aliases cover missing keys (Insert, Home/End). Browser- and OS-reserved keys are never used. GTD-only actions get extra single-letter keys in the same style. Capture is in-app only for now; a global hotkey is deferred. There are no confirmation dialogs; every action is undoable with ⌘Z, announced in a brief toast (there is no status bar). Shortcuts are discovered through a ⌘K command palette (plus Outlook's ⇧? overlay), not printed on the lists. The exceptions are the rail, where every stop shows its shortcut as a key cap, and the letter-key modes, Clarify, the Weekly Review and the focused detail pane: each carries one quiet line naming its few keys (owner's decisions after the first and fourth critiques), and a stopped Clarify lists its ways forward with their keys (add a key, clarify without Claude, file, back to the Inbox). The palette lists recently used commands first, then the current screen's own commands, then navigation, then cursor movement. Key legends show modifier symbols on every system (⌃ Control, ⇧ Shift; ⌘ and ⌥ on the Mac, ◇ for Alt elsewhere), never "Ctrl+Shift+" words (owner's decision).
- Target browsers: Firefox and Microsoft Edge (Chromium) on macOS. Both must be tested, including every shortcut.
- Data is local-first in SQLite. The API key is entered in Settings, checked against Claude, and stored server-side in `.env`. The browser only ever sees its last four characters.
- Terminology follows GTD: stuff, capture, clarify, organize, reflect, engage, next action, project, context, waiting for, someday/maybe, reference.
- Naming: next actions and projects are both written verb-first ("Call Anna about the Q3 figures", "Update the user guide for the new software"). The project title is the expected outcome; there is no separate outcome field.
- **Capture inputs:** typed text, pasted text or email, and uploaded PDF, DOCX, TXT/MD, images, .eml and .msg. A document enters as one inbox item; Clarify may split it into several outcomes, and the source file stays linked.
- **Clarify:** uses Claude Sonnet 5. The whole inbox is processed in one batch when Clarify starts, and the owner reviews one item at a time. Claude sees existing projects, areas and contexts so it can attach to them instead of duplicating. Each proposal carries an outcome (next action, new or existing project, waiting for, someday/maybe, reference, trash), a verb-first rewrite of vague captures, and a two-minute flag for anything quick enough to do right away.
- **Clarify language** (owner's request): Settings › Claude › Clarify in chooses English (the default) or Swedish. Claude writes every proposal (action and project titles, reference titles and notes) and its suggested rules in that language, whatever language the stuff was captured in, keeping names and quoted phrases as they are. Swedish proposals are written as a Swede would note them down, in the imperative ("Ring Anna om Q3-siffrorna"). Proposals made in the other language are made again the next time Clarify with Claude runs. Without an API key, Clarify with Claude opens straight on its ways forward (add a key, clarify by hand, file, back), never on a reading state. The interface itself stays in English.
- **One step per action** (owner's rule, GTD): a proposed next action is never two steps. Anything that takes more than one action is a project, so "Check effort and quote a solution" becomes a project with the actions "Check effort" and "Quote a solution". The prompt says so, and the server enforces it on every proposal: a title that joins verb-led steps (and, then, ;, or in Swedish och, sedan, därefter) is split into one action per step, placed in its project or a new project named after the original title; the start date stays on the first step and the due date moves to the last. Joined objects ("Call Anna and Per", "Buy milk and bread") stay one action.
- **Learning:** repeated identical corrections produce a suggested rule. The owner must approve it, and approved rules can be edited in Settings. Nothing is learned silently.
- **Done items:** leave the active lists but stay in a collapsed Done group on their project and in a searchable, dated Done log. The Weekly Review uses this log.
- **Recurring actions:** the next occurrence is created when the current one is marked done, with its dates moved forward. Recurrence is set as natural text ("every 3 months", "every mon").
- **Waiting For:** every item must name who or what it is waiting on. Every way into Waiting For asks for it first (moving, delegating, creating directly, filing from the Inbox, Clarify), and cancelling changes nothing. Items also record since when (set automatically), a follow-up date that resurfaces the item as something to chase, and an optional project link. A waiting item counts as its project's next step, so the project isn't flagged as stalled.
- **Tickler:** any item can get a "bring back on" date, and on that date it returns to the Inbox. Defer (start) dates hide next actions until their date.
- **Areas of focus:** projects belong to areas (#Work, #Home, #Health…; shown with a # as contexts are with an @, owner's decision), which group the Projects list and the review. There is no Areas page (owner's decision: grouping Projects by area already shows it); areas are added from any area picker and renamed, reordered or deleted in Settings › Areas.
- **Project support:** each project has a notes page and attached files.
- **Weekly Review:** a guided checklist that runs get clear → projects → Waiting For → Someday/Maybe → upcoming dates. Claude pre-flags stalled projects, stale waiting items and vague actions, and suggests edits the owner accepts or rejects one by one. The date of the last review is shown.
- **Export:** everything can be exported as Markdown (one file per list) plus a JSON dump, so there is no lock-in. Automatic backup and import are not in scope for now.
- **Theme:** follows the macOS appearance, with a light daytime theme and a dark evening theme, both designed in their own right.
- **Not in scope yet:** global capture hotkey, multiple devices, import.
- No clarification writes "Captured: …" into an action's notes (owner's decision). Clarifying by hand carries the item's own notes (everything under its first line) over to the first action as they are; a one-line capture leaves the notes empty. Clarify with Claude leaves the notes alone.
- **Calendar** (owner's request): GTD's hard landscape, second in the rail right after the Inbox (⌃2), because it is checked before the lists are worked. Week, month and year views of the dates the system holds: an action's start (defer) and due, a project's start and due (projects gained a start date for it), Waiting For follow-ups and Someday ticklers. Start and due draw one bar across the days between; either end drags to change that date, the bar drags to move both. Done and deleted work stays off it. Weeks start on Monday, or Sunday in Settings › Calendar.
- On Projects and in the Weekly Review's Projects step, ⇧W adds a Waiting For item straight to the project under the cursor (what, then who or what; waiting since today), as T and N add a next action; a waiting item counts as the project's next step.
- A Waiting For item can be added from anywhere with ⌥W (owner's request): what you're waiting for, who or what you wait on (required, as everywhere in Waiting For; recent names are offered), then its project if any. It is waiting since today; a follow-up date is set on the item.
- A next action can be added from anywhere with ⌥T (owner's request): what to do, its context (required, as everywhere), then its project if it has one ("No project" first; a new name creates the project). It lands on Next Actions and the view stays where it was.
- A project can be started from anywhere with ⌥N (owner's request): its outcome (verb first), its area or none, then its first next action with a context, as GTD asks of every project; Esc at that step keeps the project without one. On the Projects list N still adds one in place.
- When clarifying by hand, an item can be made a project directly (⇧P, or File as › Whole item → New project; owner's request): the project takes the item's name, the proposed actions go into it, and the first action is ready to be named as the next step.
- A next action that turns out to need more than one step can be turned into a project (⇧P, the Move picker, ⌘K; owner's request): the action becomes the project's outcome and carries its notes, files, start/due dates, tickler and area (from the project it was in, whose name is noted); the first next action is asked for at once, keeping the old action's context.
- Deleted items are kept for a week by default in the Trash (⌃9), adjustable in Settings (1–365 days), and can be restored where they were until then; after that the server removes them and their files (owner's request).
- Done works as in classic Outlook (owner's decision): a done action stays on its list, greyed and struck through at the bottom of its group, until archived; each action list can show or hide its done actions and archive them to Done (⇧E). Done holds only archived actions. Existing done actions were treated as already archived.
- Each view has its own address (#inbox, #projects, #reference…), so the browser's Back and Forward move between views and a reload or bookmark lands on the same list (owner's request). Clarify has an entry (Back leaves it) but can't be reopened from an address, so it lands on the Inbox; search is a query, not a place, and adds no entry. The tab title names the view ("Projects · Stiltje").

## Brand Commitments

- Colour scheme: very neutral, near-white and grey with the faintest cast of the pond's water, harmonised with it but never reading as blue (owner's decision). Colour appears only where it makes a difference: blue for focus and selection, red for trouble, the traffic-light lamps. There is no yellow in the interface.
- Project health reads like traffic lights: green = has a next action, amber = only waiting on others, red = stalled.
- The name is **Stiltje**, Swedish for dead calm: the wind has dropped and the water lies flat. It is David Allen's "mind like water" at rest (owner's choice, replacing In-Tray). The paper desk kit (label tape, folders, rubber stamps, steel) is scrapped (owner's decision). A full water-first redesign was also explored and rejected, so the only image is the rail's pond; the rest of the interface is quiet neutrals tuned to it. Internal names (`gtd`, `/opt/gtd`, the service units, the domain) stay.
- Copy never says where Stiltje runs or where things are kept: no "this Mac", "the computer", "the server", "the VPS", ".env" or "disk" in tooltips, messages or settings (owner's rule). It runs locally and on a server, so any such wording is wrong somewhere. Say what happens ("saves it", "only its last four characters are shown"), not where.

## Product Principles

1. **Capture must be instant.** Getting something into the inbox should never require deciding anything.
2. **Claude proposes, the owner disposes.** Every AI outcome is a reviewable suggestion, never a silent change.
3. **Density over decoration.** The lists are working surfaces: many rows visible and editable in place.
4. **Keyboard first, everything has a shortcut.** If an action can't be done from the keyboard, it isn't finished.
5. **Faithful to GTD.** Use the method's vocabulary and flow rather than inventing a new productivity model.
6. **The owner's data stays with the owner.** It is local-first and portable.

## Accessibility & Inclusion

Full keyboard operability is a product requirement, not just an accessibility nicety. Focus must always be visible, and nothing can trap it. Every command must be discoverable from the keyboard (a shortcut reference and command palette). Semantic markup (grid/listbox roles) should keep the lists usable with a screen reader: the active list holds real keyboard focus and points `aria-activedescendant` at the cursor row, "selected" means ticked rows only (a plain move or click clears them, as in Finder and Explorer; ⇧ extends a range, ⌘/Ctrl-click ticks one, and a drag draws a selection rectangle, adding to the selection with ⌘/Ctrl), and every view change lands focus on the new list.
- The Weekly Review's progress survives closing the tab (a review untouched for a week starts over). Finish leads with what was cleared ("4 of 6 steps clear · 3 items clarified"), then lists what is still open. It never claims more than is true: the tape reads "Ready to record" while steps are open, and the recorded message only says "Your system is current" when none are (otherwise it says how many were left open). Get clear lists the Inbox as a list like the other steps (kind, subject, files, captured); V files the focused or ticked items, E marks them done (two-minute rule) and Delete trashes them, all without leaving the review. K (Clarify) and ⌥K (Clarify with Claude) run Clarify inside the step, under the review's step bar; Esc returns to the list (owner's decision: clarifying and filing never take the owner out of the review). The Projects step shows each project's next action, or who it waits on. The rail says "not yet" before a first review and only turns red once a review is more than a week old.
- Toasts name the item when there is one ("“Pay the VAT for Q3” done"). ⌘Z returns the cursor to the restored row. A command on a group heading says so instead of doing nothing, and Esc from the capture bar says the draft is kept.
- Filing (V, "File", in the Inbox, or from an Inbox item's detail pane) covers the whole clarify decision in one picker, in GTD order: a list; done now (two-minute rule) or trash; an existing project; or a new project (type its name, as the placeholder says; the item becomes its first action). Move and File as list destinations in the same order with the same names.
- The rail is a status panel: the Inbox (an ordinary rail item with its count), the lists in order of use with counts only where they ask for something (overdue, to chase, stalled, done today), and a system check (review age, oldest Inbox item; stalled projects and follow-ups due show on the Projects and Waiting For stops instead) whose rows open where each is fixed. On phones it becomes a bottom tab bar (Inbox, Next, Waiting, More).
- The detail pane opens with focus on the pane, not in a field: each field shows its own key as a small key cap beside its label while the pane has focus, and that key opens its picker, Tab or F2 edits the subject, and one Escape closes the pane and returns to the row. The rail, when active, holds real keyboard focus on its cursor.
- Claude never runs on its own: every Claude call starts from an explicit owner action (⌥K to clarify with Claude, R at the end of Clarify or ⇧K in Settings to suggest rules from corrections). The Weekly Review never uses Claude.. Opening a view, finishing a queue or adding a key never calls Claude by itself, except "Add your key and start" in a stopped Clarify, which says so.
- When clarifying, every next action must have a context (owner's rule). In Clarify, a next action without one shows its Context chip as "needed" in alert red, and ⌘↵ won't accept: it moves to that action and opens the context picker, which has no "No context" option and pre-selects nothing. Filing with V as a next action, into a project, or as a new project's first action asks for the context first; Esc files nothing. A new context can be typed there. Waiting For keeps its own rule (who or what you wait on); done-now, someday, reference and trash need no context.
- Claude is optional, Clarify included. **K** is Clarify: you decide, one item at a time, on the Clarify screen; each item starts as "Your decision" (actionable, with its first line as the first next action) and you set the project, context, dates, disposition or extra actions, then ⌘↵. Nothing is sent to Claude and nothing is logged as a correction. **⌥K** is Clarify with Claude: the same screen with Claude's proposals; without a key it stops and offers to add one, or K to clarify without Claude. Filing (V) is simply "File"; there is no Claude version of it.
- Without a key, Clarify with Claude offers to add one (or K to clarify without Claude).
- A Weekly Review step is struck through only when it has been visited and nothing in it is left open: inbox empty, no stalled or flagged projects, no overdue next actions, no follow-ups due, no someday items due back, and nothing in Upcoming already past its date. Overdue counts as open with or without Claude. Open steps show their count, and each step's date column says which date it is (Due, Follow up, Comes back).
- The Weekly Review's checks are built in, with no Claude (owner's decision). A project is **stalled** when it has no next or waiting action, or when nothing in it has been touched (edited or completed) for the stall threshold, 3 weeks by default and set in Settings › Weekly Review › Stalled after (type any whole number of weeks, 1–52). Every action records when it was last touched. The review also notes overdue next actions, follow-ups due, next or waiting items untouched for the threshold, and someday items due back. The stalled lamp and badge use the same rule everywhere (Projects, the rail's system check, the review). A project with a start date hasn't begun until that day is over (owner's decision, GTD's "a calendar entry is a next step"): before then it can't be stalled, whatever it holds, so a project waiting for a booked meeting gets the meeting's day as its start and is only flagged from the day after, if the meeting left no next action. Its idle clock runs from its start date (or creation, if later). It is still listed in every Weekly Review with its start date, so a start date can't quietly park it; on the day it starts, without a next action, it asks for one ("Starts today: add a next action").
- The Weekly Review is resumable: leaving it to fix something (a list, Clarify, a project) and coming back returns to the same step with the same struck steps (Claude plays no part in it).
- Finish lists the steps still open (keys 1–6 jump to them), a tally of what the review did (clarified, done, added, completed) and records with ⌘↵. In the Projects step, N gives the focused project a next action directly.
- The "waiting on" prompt pre-selects nothing (unless the item already has a name, or you add inside a waiting-on group): Enter alone never picks someone by accident. The Move picker marks the item's current list and project.
- Overdue dates say so to screen readers, not only in red. Help, the palette and pickers are proper dialogs and comboboxes; a stopped Clarify is announced and focuses its first way forward.
